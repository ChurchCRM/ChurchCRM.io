# Skill: Metadata Foundation (titles, OG/Twitter, JSON-LD, robots)

## Context

Issue #67 audited the site's search-facing metadata (`layouts/partials/head.html`, plus `layouts/_default/faq.html` and `layouts/blog/single.html`) against actual product truth in `ChurchCRM/CRM`, and against OG/Twitter/schema.org correctness. This documents what was found and the rules to keep it correct going forward.

## Critical: `jsonify` inside `<script type="application/ld+json">` needs `| safeJS`

**The bug:** `"field": {{ .Value | jsonify }}` inside a hand-written JSON-LD `<script>` block produces double-escaped, invalid values — e.g. `"headline": "\"My Post Title\""` instead of `"headline": "My Post Title"`. Go's `html/template` package (which Hugo uses for `.html` layouts) applies its own contextual auto-escaping inside `<script>` tags; when `jsonify` has already produced a complete, quoted JSON string, that auto-escaper re-escapes the quote characters `jsonify` added, corrupting the value.

**The fix:** always pipe through `safeJS` after `jsonify` when the result is inlined directly into hand-written JSON (not passed to Hugo's own `jsonify` on a whole `dict`/`slice` structure — that pattern, used correctly in `layouts/blog/single.html` for `$articleSchema`, doesn't need it because the *entire* script body comes from one `jsonify` call, not individual fields spliced into hand-typed JSON):

```go
{{/* ✅ CORRECT */}}
"headline": {{ .Title | jsonify | safeJS }},

{{/* ❌ WRONG — silently produces invalid/garbled JSON-LD */}}
"headline": {{ .Title | jsonify }},
```

This bug existed in 7 places across `head.html` and `faq.html` before issue #67 (home page description, blog headline/description/author name, breadcrumb item names on every non-home page, and the entire FAQPage question/answer schema) — it was invisible in the rendered page (the meta tags and visible text were fine) and only showed up in the actual `<script type="application/ld+json">` payload, which is why it went unnoticed. `scripts/check-metadata.mjs` now parses every JSON-LD block on every built page with a real JSON parser specifically to catch this class of bug again.

**Rule:** any time you add a new `jsonify`'d field to one of these hand-written JSON-LD blocks, add `| safeJS` and then verify with `node scripts/check-metadata.mjs` — a passing build does not mean the JSON-LD is valid; only a JSON parser does.

## og:type

Only actual blog posts (`.Section "blog"` and `.IsPage`) get `og:type="article"`. Every other page — including product/marketing pages, the FAQ, install/demo guides, and policy pages — gets `og:type="website"`. The old logic (`cond (eq .Kind "home") "website" "article"`) marked *every non-home page* as an `article`, which is a misuse of the OG type for pages that aren't editorial/dated content.

## og:image / twitter:image default

The site-wide fallback (used whenever a page doesn't set `featured_image` in front matter) is `images/home-feature.png` (1000×450, ~2.2:1 landscape) — **not** `media/android-chrome-512x512.png` (a 512×512 square app icon). `twitter:card` is declared as `summary_large_image`, which expects a landscape image; a square icon renders poorly/gets cropped in that card format. If you add a new default social-share image, keep it landscape (roughly 1.91:1–2:1, well above 300×157px) — not a square logo.

**Also check that `featured_image` frontmatter values actually resolve to a real file.** `scripts/check-metadata.mjs` checks every rendered `og:image` against the built `public/` output and fails if the file doesn't exist — this caught three blog posts (`2026-04-20-churchcrm-plugin-ecosystem.md`, `2026-04-22-kiosk-check-in-for-all-groups.md`, `2026-04-27-introducing-the-export-hub.md`) referencing images that were never added, which broke both their social-share image *and* their card image on `/blog/` (the listing template also renders `featured_image` directly as an `<img src>`).

## robots meta — intentional, non-default cases

`head.html` emits `noindex, follow` only for `.Kind "taxonomy"` and `.Kind "term"` (the auto-generated `/tags/` list and each individual `/tags/<name>/` page). Every other kind gets `index, follow`. This is intentional: tag pages are thin, auto-generated aggregation pages with no unique content of their own — indexing them creates low-value pages in search results and dilutes the real content they aggregate. Everything else on the site is meant to be discoverable.

The alias/redirect stub pages (e.g. `public/es/church-management-software.html`, generated by Hugo's own `aliases:` mechanism per `content/redirect-mapping.csv`) don't go through `head.html` at all — they're a separate, minimal Hugo-generated template (canonical + meta-refresh only, no robots meta tag). That's fine as-is: the canonical tag alone is sufficient signal, and these pages are already excluded from the sitemap (see `redirect-strategy.md`).

## JSON-LD `SoftwareApplication.operatingSystem`

Verify this kind of substantive product claim against `ChurchCRM/CRM` before trusting it, not just against what's already on the site. It previously read `["Linux", "Windows (via Docker)", "macOS (via Docker)"]`, implying Windows/macOS are supported production platforms. The site's own FAQ (`content/en/faq.md`) already had a more careful, deliberately-hedged answer: Docker is for **local testing or single-user setup only**, and there is **no officially maintained production Docker image**. The JSON-LD claim contradicted the FAQ's own framing. Corrected to `"operatingSystem": "Linux"` — the one platform actually described as production-supported.

**Lesson**: when a schema.org claim and a page's own prose disagree, the prose (written for humans, more likely to have been reviewed for nuance) is usually the one to trust — check both, and reconcile toward the more careful one, not just whichever was easier to leave alone.

## Cross-checking factual/tabular claims against `ChurchCRM/CRM`

Two more discrepancies found this way, worth the pattern going forward — grep both repos for the same table/fact and diff by eye, don't assume a copy stayed in sync with its source:

- `content/en/security.md`'s "Supported Versions" table was missing an entire row (`5.0–5.2.x`) present in the authoritative `ChurchCRM/CRM/SECURITY.md`. Fixed by adding the missing row to match exactly.
- `content/en/security.md`'s Discord link (`discord.gg/tuWyFzj3Nj`) and `ChurchCRM/CRM/SECURITY.md`'s Discord link (`discord.gg/w4mmYPSnE`) don't match. The CRM repo's own `README.md` badge uses `tuWyFzj3Nj` (matching churchcrm.io), which is decent evidence the `SECURITY.md` invite is the stale one — but this wasn't changed here (churchcrm.io's own copy already uses the apparently-current link) and needs a human to actually test both invites before touching the CRM repo's `SECURITY.md`.
